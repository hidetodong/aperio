# TECH_PLAN — ITER-0012

方案状态: pass

## Design Decisions

- 继续用 marked 把 Markdown 转成网页，再用 DOMPurify 清洗。图出不来不是转换库的问题。
- 只在清洗之后改图片地址。相对地址按文件所在目录拼绝对路径，再交给现成的 `fileUrl`。https、http、data、blob 保持原样。没有以 `/` 开头的路径不改，压缩包里的正文因此不受影响。
- 文件地址的转换留在界面层。渲染函数收一个可选的 `toFileUrl`，测试里用假函数，不碰 Tauri。转换抛错时保留原地址。
- 图片名单只加 `https:`。`script-src` 仍是 `'self'`。
- 标题守着现有字号上限 20px：一级 20px，二级 17px，正文 15px。表格用细框线。链接用已有的强调色 `--accent`。
- 用户 2026-10-28 对上述取舍说了「按这个改」。审查方式是 user-ack。

### Plan Admission

- AC 覆盖：AC1 由路径改写和 `TextView` 传入打开文件的路径覆盖。AC2 只改 `tauri.conf.json` 的图片名单。AC3 只改 `App.css` 的文章规则。AC4 不改清洗规则，原测试继续守。
- 假设：打开的 Markdown 路径以 `/` 开头。本机阅读器只在 Mac 上跑，这个假设成立。
- 放弃的做法：不把外链图下载成内嵌数据，避免多一次网络和缓存。不把 https 加进脚本名单。不把标题放大超过 20px。
- 失败：转换函数抛错就留原地址，文章仍能看，只是那张图继续缺。上级目录 `..` 按真实路径折叠，不单独拦。
- 影响面：主窗口打开的 Markdown 会改图片地址。压缩包预览不传文件地址函数，行为与现在相同。图片名单变宽会影响整个窗口里的图片，这是点头过的。
- 验证盲区：自动测试看不到真实窗口里徽章有没有画出来，也看不到内容安全策略有没有在系统窗口里生效。
- Verdict：pass。四条验收都有落点，没有未解决的必须修改项。

## Failure Paths

- `toFileUrl` 抛错：这张图保持原地址，其余正文照常显示。
- 相对路径解码失败：这张图保持原地址。
- 图片文件实际不存在：浏览器显示坏图，不拖垮阅读区。
- 压缩包内的 Markdown：路径不以 `/` 开头，不改写。

## Test Strategy

- 渲染测试覆盖同一目录、上级目录、绝对路径、https 原样、转换失败时保留原地址，以及脚本和事件属性被去掉。
- 另用测试读取图片名单、脚本名单，以及文章标题、表格、链接的样式规则。
- 不在这次启动系统窗口。真实徽章是否画出，留到有人打开 README 时看。
